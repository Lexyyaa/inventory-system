# 결정 기록 — 요구사항이 모호하거나 명시되지 않아 정한 것

과제 원문에서 답이 없거나 해석이 필요한 지점, 재고관리 시스템에서 발생할 수 있는 주요 상황을 정리하고 업무 규칙을 결정한다.

---

## 1. 문제 정의

재고관리 시스템에서 가장 중요한 것은 재고를 증가시키고 감소시키는 기능 자체보다 여러 요청이 동시에 발생하더라도 실제 재고와 시스템이 관리하는 재고가 어긋나지 않는 것이다.

특히 다음 상황을 주요 문제로 본다.

* 동일 상품에 입고 요청이 동시에 들어오는 경우
* 동일 상품에 출고 요청이 동시에 들어오는 경우
* 아직 등록되지 않은 상품에 동시에 입고 요청이 들어오는 경우
* 입고와 출고가 동시에 발생하는 경우
* 재고가 부족한 상태에서 출고 요청이 들어오는 경우
* 재고가 변경되는 시점과 사용자가 재고를 조회하는 시점이 다른 경우

--- 

## ADR-01. 상품코드의 유일 범위

### 예상 시나리오

업체 A와 업체 B가 각각 `A001`이라는 상품코드로 상품을 등록하려 한다.

```text
업체 A / A001 / Apple
업체 B / A001 / Apple
```

상품코드를 시스템 전체에서 유일하게 관리하면 서로 다른 업체의 상품코드가 충돌하게 된다.

### 선택지

* A: 상품코드를 시스템 전체에서 유일하게 관리한다
* B: 업체(Tenant) 내부에서 상품코드를 유일하게 관리한다

### 트레이드오프

* A: 코드 하나가 상품 하나를 가리켜 식별이 단순하다. 대신 먼저 등록한 업체가 코드를 차지하므로 뒤에 온 업체는 쓰던 코드를 바꿔야 하고, 다른 업체의 코드가 있다는 사실이 드러난다
* B: 업체가 쓰던 코드를 그대로 쓸 수 있다. 대신 상품을 찾을 때 항상 업체와 상품코드를 함께 봐야 한다

### 최종 결정: B

상품코드는 업체 내부에서 유일한 식별자로 관리한다.

```text
업체 A / A001
업체 B / A001
```

은 허용한다.

```text
업체 A / A001
업체 A / A001
```

은 허용하지 않는다.

### 결정 이유

과제 자체에는 업체가 명시되어 있지 않지만, 물류 시스템에서 상품코드는 업체의 기존 상품코드를 그대로 사용하는 상황을 고려할 수 있다.

시스템 전체에서 유일하게 관리하면, 이미 다른 업체가 쓰는 코드를 가진 업체가 서비스를 도입할 때 상품코드를 바꿔야 한다.

또한 대상 시스템이 여러 고객사를 대상으로 확장될 수 있는 구조를 고려하여 상품코드의 유일 범위를 업체로 한정한다.

### 영향

* Product는 소속 업체를 가진다
* 업체마다 같은 상품코드를 사용할 수 있다
* 모든 상품 관련 요청은 요청한 업체 안에서 해석한다
* 다른 업체에만 있는 상품코드로 출고하거나 조회하면 상품이 없는 것으로 처리한다

## ADR-02. Tenant Context를 어떻게 전달할 것인가

### 예상 시나리오

같은 `A001`이 여러 업체에 존재할 수 있기 때문에 재고 조회나 입출고 요청이 어느 업체의 요청인지 구분해야 한다.

### 선택지

* A: URL에 Tenant 정보를 포함한다
* B: Request Header로 Tenant 정보를 전달한다
* C: 인증/인가 시스템을 구현하고 인증 정보에서 Tenant를 추출한다

### 트레이드오프

* A: 명시적이지만 모든 API URL에 Tenant 개념이 노출된다
* B: API 구조를 단순하게 유지할 수 있다
* C: 실제 서비스에 가장 가까우나 인증 시스템 자체가 이번 과제 범위를 크게 늘린다

### 최종 결정: B

MVP에서는 다음 Header를 통해 Tenant Context를 전달한다.

```http
X-Tenant-Id: tenant-001
```

### 영향

인증/인가 기능 자체는 구현하지 않는다.

실제 서비스로 확장할 경우에는 클라이언트가 임의로 Tenant를 지정하는 방식이 아니라 인증 토큰 등의 인증 정보에서 서버가 Tenant Context를 결정하는 구조로 변경할 수 있다.

## ADR-03. Product와 Inventory를 분리할 것인가

### 예상 시나리오

상품의 이름과 상품코드는 자주 변경되는 값이 아니지만 재고 수량은 입고와 출고마다 변경된다.

또한 향후 물류 기능이 확장되면 하나의 상품에 창고별 재고나 예약재고 등이 추가될 수 있다.

### 선택지

* A: Product에 현재 재고 수량을 함께 관리한다
* B: Product와 Inventory를 분리한다

### 트레이드오프

* A: 초기 구조가 단순하다
* B: 구조가 한 단계 늘어나지만 상품 정보와 재고 상태의 책임을 분리할 수 있다

### 최종 결정: B

```text
Tenant
  └── Product
        └── Inventory
```

구조로 관리한다.

Product는 상품의 식별 및 기본 정보를 관리하고 Inventory는 현재 재고 상태를 관리한다.

### 영향

현재 재고의 기준값은 `Inventory.quantity`가 된다.

향후 창고, 로케이션, 예약 등의 요구사항이 추가되더라도 Inventory를 중심으로 확장할 수 있다.

## ADR-04. 별도 상품 등록 기능을 제공할 것인가

### 예상 시나리오

신규 상품에 대한 입고 요청이 들어온다.

과제에서는 등록되지 않은 상품이면 신규 상품으로 등록한 후 입고하라고 되어 있다.

### 선택지

* A: 상품 등록 API를 별도로 제공한다
* B: 최초 입고 과정에서 상품을 생성한다

### 트레이드오프

* A: 상품 생성과 입고의 책임이 분리되지만 API와 처리 단계가 늘어난다
* B: 과제에서 요구한 신규 상품 입고 흐름을 하나의 업무로 표현할 수 있다

### 최종 결정: B

별도의 상품 등록 API를 만들지 않고 신규 상품의 최초 입고 요청에서 Product를 생성한다.

### 영향

입고 요청은 다음 두 경우를 모두 처리한다.

```text
기존 상품
→ 재고 증가

신규 상품
→ 상품 생성
→ 재고 생성 및 증가
```

상품 정보만 별도로 변경하는 기능은 MVP에 포함하지 않는다.

입고 요청은 아직 등록되지 않은 상품을 가리켜야 하므로, 상품은 시스템이 부여하는 id가 아니라 요청자가 정하는 상품코드로 식별한다.

시스템 내부 식별자는 응답에 노출하지 않는다.

---

## ADR-05. 동일한 신규 상품에 동시에 입고 요청이 들어오는 경우

### 예상 시나리오

아직 등록되지 않은 `A001`에 다음 요청이 동시에 들어온다.

```text
A001 / +10
A001 / +20
A001 / +30
```

상품이 여러 번 생성되어서는 안 되며, 세 건의 입고 수량도 모두 반영되어야 한다.

### 선택지

* A: 애플리케이션에서 상품 존재 여부를 먼저 확인하고 없으면 생성한다
* B: 상품의 유일성은 데이터 저장소에서 보장하고, 생성 경쟁을 처리한다

### 트레이드오프

* A: 구현이 직관적이지만 동시에 확인하면 둘 이상의 요청이 모두 "없음"으로 판단할 수 있다
* B: 동시에 같은 상품을 생성하려는 상황에서도 최종적으로 하나의 상품만 남도록 할 수 있다

### 최종 결정: B

같은 업체의 동일한 `productCode`는 하나의 상품만 존재하도록 보장한다.

동시 신규 상품 생성과 관련된 상품 유일성은 데이터 저장소의 제약을 기준으로 보장한다.

### 영향

상품 중복 생성 방지와 각 입고 요청의 수량 반영을 별개의 문제로 다룬다.

즉,

```text
Product
→ 하나만 생성

Inventory
→ +10 +20 +30
→ 최종 60
```

이 되어야 한다.

먼저 등록된 상품이 기준이 되며, 나머지 요청은 기존 상품에 대한 입고로 처리한다.

* 나머지 요청의 상품명이 먼저 등록된 상품명과 다르면 상품명 불일치로 거부한다
* 어느 요청이 먼저 등록될지는 보장하지 않는다

## ADR-06. 입고 요청은 단건으로 처리한다

### 예상 시나리오

한 업체가 동시에 여러 상품을 입고할 수 있다.

예:

```text
A001 +10
A002 +20
A003 +30
```

이를 하나의 요청으로 묶을지 상품별 요청으로 나눌지 정해야 한다.

### 선택지

* A: 한 요청에서 여러 상품을 처리한다
* B: 한 요청에서 하나의 상품만 처리한다

### 트레이드오프

* A: 네트워크 요청 수를 줄일 수 있지만 부분 성공, Transaction 범위, 여러 상품의 처리 순서 등을 추가로 정의해야 한다
* B: 처리 단위와 실패 범위가 명확하며 현재 과제의 핵심인 재고 정합성에 집중할 수 있다

### 최종 결정: B

MVP에서는 한 번의 입고 요청이 하나의 상품만 처리하도록 한다.

### 영향

입고 요청은 다음 정보를 처리한다.

```text
상품코드
상품명
입고 수량
```

다건 입고는 MVP에 포함하지 않는다.

향후 다건 입고가 필요해질 경우 다음 정책을 별도로 정의한다.

* 전체 성공/부분 성공 여부
* 전체 Transaction 여부
* 동일 요청 내 중복 상품 처리
* 여러 상품을 동시에 처리할 때의 순서와 동시성

---

## ADR-07. 출고 요청은 단건으로 처리한다

### 예상 시나리오

하나의 출고 작업에서 여러 상품이 필요할 수 있다.

```text
A001 -10
A002 -20
A003 -30
```

그러나 다건 요청은 각각의 상품 재고가 모두 충분한지, 일부만 처리할지, 하나의 작업으로 묶을지 추가적인 업무 규칙이 필요하다.

### 최종 결정

MVP에서는 입고와 동일하게 한 번의 출고 요청이 하나의 상품만 처리하도록 한다.

### 결정 이유

현재 과제의 핵심은 다건 주문 처리 자체가 아니라 한 상품의 재고를 동시 요청 상황에서도 정확하게 증감시키는 것이다.

### 영향

다건 출고는 후속 확장 영역으로 남긴다.

---

## ADR-08. 기존 상품의 상품명이 다른 입고 요청

### 예상 시나리오

이미 다음 상품이 등록되어 있다.

```text
A001 / Apple
```

그런데 같은 업체의 입고 요청에서:

```text
A001 / Samsung / +10
```

이 들어온다.

### 선택지

* A: 입고 요청의 상품명으로 Product를 변경한다
* B: 기존 Product의 상품명을 유지하고 입고만 처리한다
* C: 서로 다른 상품 정보이므로 입고를 거부한다

### 트레이드오프

* A: 입고 요청이 상품 master 정보까지 변경하게 된다
* B: 요청자가 잘못된 상품명을 보내도 데이터가 조용히 처리된다
* C: 잘못된 상품 정보가 재고 처리까지 이어지는 것을 방지할 수 있다

### 최종 결정: C

`productCode`가 이미 존재하는 경우 기존 상품명을 상품의 기준 정보로 사용하며, 요청된 상품명이 다르면 입고를 처리하지 않는다.

상품명은 대소문자와 공백까지 정확히 같을 때만 같은 상품명으로 본다.

### 영향

입고 API는 상품 master 정보를 변경하지 않는다.

상품 정보 변경 기능이 필요해질 경우 별도의 업무와 API로 분리한다.

## ADR-09. 재고 부족 출고는 어떻게 처리할 것인가

### 예상 시나리오

현재 재고가 10개인데 11개 출고 요청이 들어온다.

### 선택지

* A: 가능한 만큼만 출고한다
* B: 요청 전체를 실패시킨다

### 트레이드오프

* A: 부분 출고가 가능하지만 실제 출고 수량과 요청 수량이 달라지고 추가 업무 규칙이 필요하다
* B: 하나의 요청이 명확하게 성공 또는 실패한다

### 최종 결정: B

출고 요청 수량 전체를 처리할 수 있을 때만 출고한다.

예:

```text
재고 10
출고 요청 11

→ 출고 실패
→ 재고 10 유지
```

### 영향

재고 부족은 부분 출고가 아닌 충돌 상황으로 취급한다.

## ADR-10. 동시 출고에서 무엇을 보장할 것인가

### 예상 시나리오

현재 재고가 10개이고 다음 요청이 동시에 들어온다.

```text
요청 A: -10
요청 B: -10
```

두 요청이 모두 성공하면 실제 재고보다 많은 출고가 발생한 것이다.

### 문제

단순히

```text
재고 조회
→ 출고 가능 여부 확인
→ 재고 차감
```

순서로 처리하면 동시에 여러 요청이 같은 재고를 기준으로 판단할 수 있다.

### 선택지

* A: 애플리케이션에서 재고를 조회하고 수정한다
* B: 재고를 잠근 후 수정한다
* C: 재고가 충분하다는 조건과 차감을 하나의 변경 작업으로 처리한다

### 트레이드오프

* A: 구조는 단순하지만 동시 요청에서 재고 상태가 충돌할 수 있다
* B: 명시적으로 충돌을 직렬화할 수 있지만 현재 요구사항보다 제어 범위가 크다
* C: 현재 재고가 충분하다는 규칙과 차감을 하나의 상태 변경으로 표현할 수 있다

### 최종 결정: C

출고 가능 여부와 재고 차감이 분리된 두 단계가 되지 않도록 한다.

### 영향

동시 출고에서도 다음 조건을 지킨다.

```text
성공한 출고 총량 <= 실제 재고
```

---

## ADR-11. 동시 입고에서 무엇을 보장할 것인가

### 예상 시나리오

현재 재고가 0이고 동일 상품에 동시에 다음 요청이 들어온다.

```text
+10
+20
+30
```

### 최종 결정

정상 처리된 입고 요청의 수량은 모두 최종 재고에 반영되어야 한다.

```text
0 + 10 + 20 + 30 = 60
```

### 영향

재고 증가도 현재 값을 읽은 후 애플리케이션에서 계산하여 저장하는 방식이 아니라 동시에 발생한 변경이 서로 덮어쓰지 않도록 처리한다.

---

## ADR-12. 입고와 출고가 동시에 발생하는 경우

### 예상 시나리오

현재 재고가 10이고 동시에 다음 요청이 발생한다.

```text
입고 +10
출고 -15
```

### 문제

두 요청이 서로 상대방의 처리 과정 중간 상태를 기준으로 판단하면 안 된다.

### 최종 결정

각 입출고 요청은 자신의 Transaction 범위 내에서 재고를 변경하며, 커밋되지 않은 변경 상태를 다른 요청이 정상적인 재고 상태로 취급하지 않도록 한다.

### 영향

최종 결과는 실제로 먼저 성공하여 커밋된 상태와 이후 요청이 처리되는 순서에 따라 결정된다.

입고가 먼저 커밋되면 출고가 성공할 수 있고, 출고가 먼저 처리되면 재고 부족으로 실패할 수 있다.

이는 두 요청 중 어느 하나를 임의로 우선시키는 것이 아니라 각 요청의 실제 처리 결과에 따라 최종 상태가 결정되는 것으로 본다.

---

## ADR-13. 재고 조회 중 재고가 변경되는 경우

### 예상 시나리오

사용자가 재고를 조회하는 동안 다른 사용자가 출고한다.

```text
조회 시작
재고 = 100

출고
재고 = 90

조회 응답
재고 = 100
```

### 문제

조회 응답 시점에 항상 가장 최신 재고를 반환하도록 강제할 것인지 결정할 필요가 있다.

### 선택지

* A: 조회도 재고 변경이 끝날 때까지 기다린 후 최신 상태를 반환한다
* B: 조회가 수행된 시점에 읽을 수 있는 일관된 상태를 반환한다

### 트레이드오프

* A: 조회가 재고 변경을 방해할 수 있고 조회 API의 처리 비용이 커진다
* B: 조회와 변경을 독립적으로 처리할 수 있다

### 최종 결정: B

재고 조회는 조회 시점의 일관된 현재 상태를 반환하는 단순 조회로 정의한다.

조회가 완료된 직후 다른 요청으로 재고가 변경되는 것은 정상적인 상황으로 본다.

### 영향

재고 조회에는 별도의 비관적 잠금을 사용하지 않는다.

---

## ADR-14. 오류를 어떻게 구분할 것인가

### 예상 시나리오

다음 요청은 모두 정상적으로 처리할 수 없다.

* 잘못된 수량
* 존재하지 않는 상품
* 재고 부족
* 기존 상품과 다른 상품명
* Tenant 정보 없음

단순히 모든 실패를 같은 오류로 반환하면 클라이언트가 다음 행동을 결정하기 어렵다.

### 선택지

* A: 모든 오류를 하나의 상태와 메시지로 반환한다
* B: 입력 오류, 대상 없음, 현재 상태와의 충돌을 구분한다

### 최종 결정: B

오류를 의미에 따라 구분한다.

```text
잘못된 요청
→ 400

대상이 존재하지 않음
→ 404

현재 재고 또는 상품 상태와 충돌
→ 409
```

---

## ADR-15. 등록되지 않은 업체의 요청

### 예상 시나리오

업체를 등록하는 기능은 MVP에 없다.

그런데 `X-Tenant-Id`에 등록되지 않은 업체 코드가 들어오거나, 헤더가 비어 있는 요청이 들어올 수 있다.

### 선택지

* A: 처음 보는 업체 코드면 업체를 자동으로 등록한다
* B: 업체는 미리 등록해 두고, 등록되지 않은 업체의 요청은 거부한다

### 트레이드오프

* A: 별도 준비 없이 요청할 수 있지만 오타 하나로 새 업체가 생겨 업체 구분이 의미 없어진다
* B: 업체를 미리 준비해야 하지만 업체 구분이 명확하다

### 최종 결정: B

업체는 시스템 기동 시 미리 등록해 둔다.

`X-Tenant-Id`가 없거나, 비어 있거나, 등록되지 않은 업체 코드면 잘못된 요청으로 처리한다.

### 영향

업체 확인은 요청 본문 검증보다 먼저 한다.

## ADR-16. 입출고 수량의 상한

### 예상 시나리오

입고 수량으로 매우 큰 값이 들어온다.

```text
A001 / +9223372036854775807
```

재고가 저장할 수 있는 범위를 넘으면 요청이 서버 오류로 끝난다.

### 최종 결정

요청 한 건의 입출고 수량에 상한을 둔다.

상한은 1,000,000,000이며, 코드에 고정하지 않고 설정으로 관리한다.

이 상한에서 재고 합이 저장 범위(BIGINT)를 넘으려면 최대 수량 입고가 약 92억 번 필요하다.

### 영향

수량이 1 미만이거나 상한을 넘으면 잘못된 수량으로 처리한다.

---

## ADR-17. 같은 요청이 여러 번 들어오는 경우

### 예상 시나리오

네트워크 재시도로 같은 입고 요청이 두 번 전달된다.

```text
A001 / +10
A001 / +10
```

### 최종 결정

내용이 같아도 각각 독립된 요청으로 처리한다.

### 영향

재시도로 같은 요청이 다시 오면 수량이 중복 반영될 수 있다.

이는 MVP의 알려진 한계로 둔다.

## ADR-18. 입출고 응답의 재고 수량

### 예상 시나리오

재고가 0인 상품에 다음 입고가 동시에 처리된다.

```text
+10
+20
+30
```

각 요청의 응답에 담는 재고 수량이 무엇인지 정해야 한다.

### 선택지

* A: 이 요청이 반영된 직후의 재고 수량
* B: 응답을 만드는 시점의 최신 재고 수량

### 트레이드오프

* A: 요청마다 자신이 만든 결과를 정확히 알 수 있다. 동시에 처리된 요청은 서로 다른 값을 받는다
* B: 모두 최신 값을 받지만 그 값에 다른 요청의 변경이 섞여 이 요청의 결과를 알 수 없다

### 최종 결정: A

입출고 응답의 재고 수량은 이 요청이 반영된 직후의 값이다.

### 영향

위 예시에서 세 응답은 처리 순서에 따라 10, 30, 60처럼 서로 다를 수 있다.

최종 재고는 조회로 확인한다.
