## 설계에 없어서 정한 것

- id 생성 방식
  - 정한 것: `GENERATED BY DEFAULT AS IDENTITY`
  - 이유: Hibernate가 PostgreSQL에 만드는 DDL과 같은 형태
- 제약 이름
  - 정한 것: `pk_` · `uk_` · `fk_` · `ck_` 접두
- seed 인코딩
  - 정한 것: `sql.init.encoding: UTF-8`
- 문구가 둘인 에러 코드의 기본 문구
  - 정한 것: 04에 먼저 나온 문구를 `ErrorCode` 기본값으로 둠
  - `INVALID_REQUEST` → "필수 요청 정보가 누락되었습니다."
  - `INVALID_QUANTITY` → "입고 수량이 허용 범위를 벗어났습니다."
  - 후속 영향: F4 출고는 detail로 출고 문구를 넘겨야 함
- 이름 없는 프레임워크 예외의 문구
  - 헤더 · 파라미터 누락 → 누락 문구
  - 타입 불일치 → 형식 문구
  - Content-Type 오류 → 형식 문구
  - multipart 오류 → 형식 문구
  - 상태 코드는 모두 400 유지
- `RESOURCE_NOT_FOUND` · `METHOD_NOT_ALLOWED` · `INTERNAL_SERVER_ERROR` 문구
  - 정한 것: 기존 문구 유지
- `Tenant` 생성 방식
  - 정한 것: 정적 팩토리를 두지 않음
  - 이유: 생성 경로가 seed뿐
- 커밋 범위
  - 정한 것: ArgumentResolver · WebMvcConfigurer를 T1-4에 포함
  - 참고: `task_list`의 T1-4 설명에는 HandlerInterceptor까지만 적혀 있음
- `INVALID_TENANT`를 던지는 위치
  - 헤더 없음 · 공백 → `TenantApplicationService`
  - 미등록 코드 → `TenantRepositoryImpl.getByCode`
- 업체 조회 트랜잭션
  - 정한 것: `@Transactional(readOnly = true)`
- 헤더 값 비교
  - 정한 것: 앞뒤 공백을 자르지 않고 정확 일치로 비교
- 테스트 전용 엔드포인트 응답
  - 정한 것: `tenantId`도 돌려줌
  - 이유: 리졸버 연결까지 확인하려고
