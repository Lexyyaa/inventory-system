# Inventory Management System

Java / Spring Boot / PostgreSQL 기반의 재고관리시스템 MVP입니다.

상품의 입고, 출고, 재고 조회를 제공하며, 동시 요청에서도 재고 정합성을 유지하는 것을 핵심 목표로 구현했습니다.

## 주요 기능과 기술 스택

### 주요 기능

| 기능 | 설명 | API |
|---|---|---|
| 상품 입고 | 기존 상품의 재고를 늘리고, 등록되지 않은 상품은 새로 만든 뒤 입고합니다 | `POST /api/v1/inventory/inbound` |
| 상품 출고 | 현재 재고 범위 안에서만 출고하고, 재고가 부족하면 거부합니다 | `POST /api/v1/inventory/outbound` |
| 재고 조회 | 요청 업체에 속한 상품의 현재 재고를 조회합니다 | `GET /api/v1/inventory/{productCode}` |
| 업체 구분 | 상품과 재고를 업체(Tenant)별로 나눕니다. 다른 업체의 상품은 보이지 않습니다 | 모든 API의 `X-Tenant-Id` 헤더 |
| 동시 요청 처리 | 같은 상품에 입고와 출고가 동시에 와도 재고가 누락되거나 음수가 되지 않습니다 | — |
| 오류 응답 | 모든 오류를 `{ "code", "message" }` 형식과 에러 코드로 돌려줍니다 | — |

요청, 응답, 에러 코드 상세는 [API 명세](docs/design/04-api-spec.md)에 있습니다.

### 기술 스택

- Java 21, Spring Boot 3.5.5, Spring Data JPA, PostgreSQL 17, Gradle, Docker Compose
- 테스트: JUnit 5, Testcontainers
- 도구: ArchUnit, Spotless, springdoc-openapi (Swagger UI)

## 핵심 설계

- **Tenant → Product → Inventory**
  - 여러 업체가 각자 쓰던 상품코드를 그대로 쓸 수 있도록, 상품코드는 업체 안에서만 유일합니다 (`UNIQUE (tenant_id, product_code)`)
  - 상품 정보(Product)와 현재 재고(Inventory)를 분리했습니다
- **재고 정합성: PostgreSQL 특성 활용**
  - 재고를 읽고 애플리케이션에서 계산해 저장하지 않고, 신규 상품 생성, 입고, 출고를 각각 SQL 한 문장으로 처리합니다
    - 신규 상품: `INSERT … ON CONFLICT DO NOTHING`
    - 입고: `INSERT … ON CONFLICT DO UPDATE SET quantity = quantity + 입고량` (UPSERT)
    - 출고: `UPDATE … WHERE quantity >= 출고량`
  - 활용한 PostgreSQL 특성
    - **조건부 UPDATE의 재평가**: 같은 행을 동시에 바꾸려는 요청은 앞 트랜잭션이 끝날 때까지 기다린 뒤, 커밋된 최신 값으로 `WHERE` 조건을 다시 확인합니다. 그래서 동시 출고에서도 재고보다 많이 빠져나가지 않습니다
    - **`ON CONFLICT`**: UNIQUE 제약 위반 예외 없이 "없으면 생성, 있으면 무시 또는 더하기"를 한 문장에서 처리합니다. PostgreSQL은 오류가 난 트랜잭션에서 다음 쿼리를 실행하지 않아, 예외를 잡고 다시 조회하는 방식은 쓸 수 없습니다
    - **`RETURNING`**: 바뀐 직후의 수량과 시각을 같은 문장에서 돌려받아, 추가 조회 없이 응답에 씁니다
  - 그래서 별도 락(`SELECT … FOR UPDATE`, 낙관적 락)이나 격리 수준 상향 없이 기본 READ COMMITTED에서 동작합니다
    - REPEATABLE READ 이상으로 올리면 같은 경합이 직렬화 오류로 끝나 재시도 로직이 따로 필요해집니다
  - DB 제약(`UNIQUE`, `CHECK (quantity >= 0)`)을 마지막 방어선으로 둡니다
- **Transaction**
  - 신규 상품 등록과 최초 입고를 하나의 작업 단위로 처리해 일부만 반영된 상태가 남지 않습니다
- **응답 수량**
  - 입출고 응답의 `quantity`는 이 요청이 반영된 직후의 재고입니다

결정 이유는 [01 분석](docs/design/01-analysis.md), 구현 방식은 [03 도메인 모델](docs/design/03-domain-model.md)에 있습니다.

## DDL

- 파일: [`src/main/resources/schema.sql`](src/main/resources/schema.sql)
  - 애플리케이션이 기동할 때 이 파일로 테이블을 만듭니다 (JPA는 스키마를 만들지 않고 검증만 합니다)
- 업체 seed: [`src/main/resources/data.sql`](src/main/resources/data.sql) (`tenant-001`, `tenant-002`)

```sql
CREATE TABLE IF NOT EXISTS tenant (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY,
    code       VARCHAR(100) NOT NULL,
    name       VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT pk_tenant PRIMARY KEY (id),
    CONSTRAINT uk_tenant_code UNIQUE (code)
);

CREATE TABLE IF NOT EXISTS product (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY,
    tenant_id    BIGINT       NOT NULL,
    product_code VARCHAR(100) NOT NULL,
    name         VARCHAR(255) NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT pk_product PRIMARY KEY (id),
    CONSTRAINT fk_product_tenant FOREIGN KEY (tenant_id) REFERENCES tenant (id),
    CONSTRAINT uk_product_tenant_code UNIQUE (tenant_id, product_code)
);

CREATE TABLE IF NOT EXISTS inventory (
    product_id BIGINT      NOT NULL,
    quantity   BIGINT      NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT pk_inventory PRIMARY KEY (product_id),
    CONSTRAINT fk_inventory_product FOREIGN KEY (product_id) REFERENCES product (id),
    CONSTRAINT ck_inventory_quantity_non_negative CHECK (quantity >= 0)
);
```

## 작업 방법

Claude Code를 활용해 SDD(Spec-Driven Development) 방식으로 진행했습니다.

- 과제를 바로 구현하지 않고 명세 문서를 먼저 썼습니다
- 그다음 명세 문서를 기준으로 기능을 하나씩 구현했습니다
- 기능 하나는 구현 → 리뷰 → 서버 실측 → 기록 순서로 끝냈고, 입고와 출고는 명세와의 추적성 점검도 거쳤습니다

작업 과정은 `docs/` 아래 세 곳에 남겼습니다.

- [`docs/task_list.md`](docs/task_list.md): 작업 목록
  - 기능(F)과 작업(T)의 순서, 각 작업이 구현하는 테스트 케이스
  - 리뷰에서 나온 지적을 모아 둔 리뷰 백로그와 처리 결과
- [`docs/ai-log/`](docs/ai-log/): 기능별 작업 로그
  - 기능마다 한 파일: 무엇을 바꿨는지, 설계와 다르게 간 것, 리뷰 및 실측 결과
- [`docs/ai-usage.md`](docs/ai-usage.md): AI 활용 내역
  - AI에게 맡긴 역할, 결과를 검증한 방법, 사람이 판단하고 수정한 것

## 작업 규칙과 작업 로그

AI가 명세 문서에서 벗어나지 않도록, 작업 목록과 규칙 파일을 따라 움직이게 했습니다.

### 작업 목록을 따라가는 방식

- [`docs/task_list.md`](docs/task_list.md)의 기능(F) 하나가 브랜치 하나, 작업(T) 하나가 커밋 하나입니다
- 작업 줄의 문장이 그대로 커밋 메시지가 됩니다
- 맨 위 **현재** 줄이 지금 할 작업을 가리키고, 작업이 끝나면 체크와 함께 다음 작업으로 옮깁니다
- 작업 줄 끝에 그 작업이 구현하는 테스트 케이스 번호를 적어, 모든 테스트 케이스가 어떤 작업에 속하는지 추적합니다

### 규칙 파일

- [`CLAUDE.md`](CLAUDE.md): 실행 명령, 묻지 않고 적용할 결정, 하지 말 것, 완료 기준
- [`src/main/CLAUDE.md`](src/main/CLAUDE.md): 패키지, 도메인, 트랜잭션, 예외, 주석 규칙
- [`src/test/CLAUDE.md`](src/test/CLAUDE.md): 테스트 이름, 종류, 단언, 동시성 테스트 규칙
- [`.claude/checklists/implementation.md`](.claude/checklists/implementation.md): 구현 체크리스트
  - 작업 중 겪은 실수를 한 줄씩 쌓아, 다음 기능의 구현과 리뷰 기준으로 씁니다

### 에이전트 (`.claude/agents`)

- `implementer`: 기능 하나를 구현하고 테스트까지 씁니다
- `reviewer`: 기능 구현 뒤 브랜치 변경분의 구조를 리뷰합니다
- `verifier`: 원문, 설계, 코드, 테스트 사이의 추적성을 점검합니다
- `doc-writer`: 명세 문서, 작업 로그, README를 씁니다

### 스킬 (`.claude/skills`)

- `/run-feature F{번호}`
  - 기능 하나를 구현 → 리뷰 → 검증 → 실측 → 기록 → 게이트 순서로 실행합니다
  - 기록 단계에서 [`docs/ai-log/`](docs/ai-log/)에 기능별 작업 로그를 남깁니다
  - 멈춤 지점에서 사용자에게 결정을 받습니다
- `/verify-http`
  - DB를 비우고 서버를 띄워 `.http`를 재연합니다
  - [`scripts/run_http.py`](scripts/run_http.py)가 상태 코드, 응답 본문, DB 값을 대조합니다
- `/wrap-up`
  - 리뷰 백로그 일괄 처리 → 제출물 작성 → 전체 점검 → 최종 게이트

## 한계와 확장 방향

### 현재 설계의 한계

- 같은 요청이 재시도되면 각각 반영됩니다
  - 멱등성은 이번 범위에서 제외했습니다
- 재고 변경 SQL이 PostgreSQL 문법(`ON CONFLICT`, `RETURNING`)입니다
  - 다른 DB로 옮기면 세 쿼리를 다시 써야 합니다
- 재고 합이 BIGINT 범위를 넘으면 500입니다
  - 한 건 상한이 10억이라 약 92억 번 입고해야 생깁니다
- 조회 경로의 `;` 뒤는 경로 매개변수로 무시됩니다
  - `/api/v1/inventory/A001;x`는 A001을 조회합니다
- `X-Tenant-Id`에 제어 문자가 오면 서버(Tomcat)가 애플리케이션에 닿기 전에 HTML 400으로 거부합니다
- 업체는 요청 헤더로 받습니다
  - 인증/인가는 범위 밖이라 클라이언트가 업체를 지정합니다

### 확장한다면

- **재고 변동 이력**
  - 입출고마다 같은 트랜잭션에서 이력을 남깁니다
  - 이력 합계와 현재 재고를 비교해 정합성을 확인할 수 있습니다
- **멱등성 키**
  - 재시도로 인한 중복 반영을 막습니다
  - 동시 재시도까지 다루려면 키 테이블의 UNIQUE 제약, 첫 응답 저장, 처리 중 상태가 함께 필요합니다
- **인증 기반 업체 결정**
  - 헤더 대신 인증 토큰에서 서버가 업체를 정합니다
- **창고/로케이션별 재고, 예약 재고**
  - 상품과 재고를 분리해 두어 재고 쪽을 넓히는 방향으로 확장할 수 있습니다
