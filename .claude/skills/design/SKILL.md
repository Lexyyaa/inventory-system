# /design — F0 설계

- 과제 원문을 분석해 결정이 필요한 지점을 드러낸다
- 사용자 결정을 받는다
- 결정을 입력으로 설계 문서와 task_list를 만든다
- 설계 점검까지 돌린다

이 스킬은 메인 세션에서 아래 순서를 **그대로** 실행한다.

- 순서를 바꾸거나 단계를 건너뛰지 않는다
- `🛑 멈춤`이 나오면 그 자리에서 사용자에게 보고하고 응답을 기다린다

시간 목표 (과제 시작 기준, 제한 시간 대비 비율)

- 제한 시간은 `00-assignment.md` 과제 정보에서 읽는다
- 분석: 약 5%
- 결정: 약 10%
- 설계 문서 · 점검: 약 25%
- 예: 3시간이면 +0:10 / +0:20 / +0:45

## 0. 사전 확인

- `docs/design/00-assignment.md`의 "원문" 아래가 비어 있으면
  - → 🛑 멈춤: "원문을 붙여넣어 주세요"
- `main`에서 `feature/design` 브랜치를 만든다
  - 이미 있으면 그 브랜치로 이동한다
  - 붙여넣은 원문(커밋 안 된 변경)은 브랜치에 그대로 따라온다
- 원문을 커밋한다
  - 대상: `00-assignment.md` + `task_list.md`
  - 메시지: `docs: 과제 원문 추가`
  - task_list T0-1 체크를 같은 커밋에 넣는다
- 그 뒤에도 커밋 안 된 변경이 남아 있으면
  - → 🛑 멈춤: 변경 목록을 보여주고 처리 방법을 묻는다

## 1. 분석

- `analyst`를 호출한다
  - 지시: "`00-assignment.md`를 분석해 `01-analysis.md`를 채운다"
  - 원문 문장이 40개를 넘으면 두 번에 나눠 호출한다
    - 1차 §0 ~ §3 / 2차 §4 ~ §5
- 끝나면 `01-analysis.md`를 직접 훑는다
  - 템플릿 자리표시(`…`, 빈 `S-` · `H-` · `C-`)가 남았는지
  - 원문 문장이 빠짐없이 §0에 있고, 문장마다 판정이 붙었는지
  - 데이터 표가 있으면 표 단위 `S-n`과 "03 §9 · data.sql 대조" 판정이 있는지
  - §2 "기능 간 교차"가 채워졌는지
  - `C-n`이 15건 이하인지, 각 `C-n`에 `추천:` 줄이 있는지
  - "기본값"으로 판정한 빈틈이 §4 "기본값 적용"에 모두 있는지
  - 문제가 있으면 `analyst`에게 한 번 더 고치게 한다
- 커밋한다
  - 메시지: `docs: 요구사항 분석`
  - task_list T0-2 체크를 같은 커밋에 넣는다

## 2. 결정 받기

🛑 멈춤: 아래 형식으로 보고하고 결정을 받는다.

- 먼저 "전부 추천대로 할까요?"를 묻는다 (AskUserQuestion)
  - 선택지: 전부 추천대로 (Recommended) / 항목별로 고르기
  - 전부 추천대로면 바로 §7에 기록하고 3단계로 간다
- 항목별로 고르면 AskUserQuestion으로 `C-n`마다 선택지를 준다
  - 첫 선택지를 추천안으로 두고 라벨 끝에 `(Recommended)`를 붙인다
  - 한 번에 4개씩 묻는다
- "기본값 적용" 목록은 보여주기만 한다
  - 사용자가 바꾸라고 한 항목만 `C-n`으로 올린다
- 사용자가 "나중에"라고 한 항목은 보류로 기록한다
  - §7 표기: `C-n → 보류 (이유)`
  - 보류 항목에 기대는 요구사항은 3단계에서 `(D-n 대기)`로 표시된다

```
## 분석 완료
- 원문 문장 S-1 ~ S-n
- 숨은 요구사항 H-1 ~ H-n
- 확인 필요 n건

## 평가 비중 상위
1. …

## 포기하면 감점이 큰 것
- …

## 결정이 필요한 항목 (C-1 ~ C-n)
### C-1. 쟁점
- 관련: S- · H-
- 1: … — 장점 / 단점
- 2: … — 장점 / 단점
- 추천: 1 — 이유

## 기본값 적용 (묻지 않고 적용)
- 빈틈 → 값
```

받은 결정은 `01-analysis.md` §7 "사용자 결정 기록"에 적는다.

- 형식: `C-n → 선택지 번호와 내용 (사용자가 덧붙인 이유가 있으면 함께)`
  - 일괄 수락 · 위임 같은 결정 경위는 적지 않는다. 고른 내용만 적는다
- 커밋하지 않는다. 5단계에서 함께 커밋한다

## 3. 설계 문서 작성

두 번에 나눠 호출한다. 한 번에 네 문서를 쓰면 길어서 중단 시 상태를 알 수 없다.

- 1차: `doc-writer`를 호출한다
  - 지시: "분석과 §7 결정을 입력으로 `02-requirements.md`를 작성한다"
  - 끝나면 `02`을 직접 훑는다
    - 자리표시가 남았는지
    - `(D-n 대기)`가 보류 결정과 맞는지
- 2차: `doc-writer`를 호출한다
  - 지시: "`02`을 기준으로 `03` → `04` → `task_list` 순서로 작성한다"
  - task_list는 F1 이하만 채운다
    - F0 블록 · **현재** 줄은 건드리지 않는다
- 보고에 "새로 필요한 결정"이 있으면
  - → 🛑 멈춤: 2단계와 같은 형식으로 묻는다
  - 받은 결정을 `01-analysis.md` §4에 `C-n`으로 추가하고 §7에 기록한다
  - `doc-writer`를 다시 호출한다
    - 지시: "이어서 작성한다. 이미 채워진 절은 건너뛴다"
- 끝나면 네 문서를 직접 훑는다
  - 템플릿 자리표시가 남았는지 확인한다
    - `{기능명}` 같은 `{…}` · 빈 표 행
    - 예시 값
      - `Xxx` · `XXX_` · `PARENT` · `CHILD`
      - `/resources` · `name` · `amount` · `items`

## 4. 설계 점검

- `verifier`를 **설계 점검 모드**로 **1회만** 호출한다
- 높음 지적만 `doc-writer`로 고친다
  - 재점검은 돌리지 않는다. 고친 내용은 메인 세션이 직접 훑는다
- 중간 · 낮음은 고치지 않는다
  - task_list "리뷰 백로그" 표에 한 줄씩 적는다 (F 칸은 `F0`)
  - `/wrap-up`에서 한 번에 처리한다
- 높음을 고치려면 새 결정이 필요하면 → 🛑 멈춤: 지적과 선택지(추천 포함)를 보고한다
  - 새 결정은 `01-analysis.md`에 `C-n`으로 추가하고 §7에 기록한다
  - `doc-writer`로 반영한다

## 5. 커밋

task_list의 F0 작업 줄 문장으로 문서별 커밋을 만든다.

- task_list는 부분 스테이징이 어려우므로 마지막 커밋에서만 add한다
- T0-3 ~ T0-5 체크박스는 마지막 커밋에 몰아 넣는다

- `docs: 요구사항 구체화 및 테스트 케이스 작성`
  - `02` + `01-analysis.md` §7 결정 기록
- `docs: 도메인 모델 및 ERD 작성` — `03`
- `docs: API 명세 및 에러 코드 작성` — `04`
- `docs: 작업 목록 작성`
  - `task_list` (T0-3 ~ T0-6 체크 포함)
  - **현재**를 `F1 / T1-1`로 옮긴다
