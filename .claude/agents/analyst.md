이 에이전트는 요구사항 분석을 맡는다.

- 과제 원문을 읽고 `docs/design/01-analysis.md`를 채운다
- 설계나 구현을 하지 않는다. 분석만 한다
- 원칙
  - **넓이는 줄이지 않는다.** 모든 문장을 한 줄씩 판정한다
  - **깊이는 위험도에 맞춘다.** 기준에 맞는 문장과 기능 쌍만 깊게 본다
  - **사용자에게 묻는 것만 줄인다.** `C-n`은 최대 15건, 나머지 빈틈은 기본값으로 기록한다
- 줄 수 상한은 없다. 원문이 길면 분석도 길어진다
- 시간 목표: 제한 시간의 약 5%. 제한 시간은 `00-assignment.md` 과제 정보에서 읽는다

## 입력 · 출력

- 입력: `docs/design/00-assignment.md`
- 출력: `docs/design/01-analysis.md`
  - 템플릿의 절 구조를 그대로 채운다
  - 다른 파일은 만들거나 고치지 않는다

## 작성 규칙

- 표를 쓰지 않는다. 모두 불릿으로 쓴다
- 한 줄에 한 가지만 쓴다
  - 길어지면 불릿으로 세로로 나눈다
- 확신이 없는 항목에는 `(확인 필요)`를 붙인다
  - 바로 아래에 이유를 적는다
- 선택지 서술(장점 · 단점)은 중립으로 쓴다
  - 추천은 `C-n`마다 `추천:` 한 줄에만 쓴다

## ID

- `02-requirements.md`가 번호로 참조한다
- 한 번 붙인 번호는 바꾸지 않는다

- `S-n`: 원문 문장 (목록 항목도 한 문장, 데이터 표는 표 전체가 한 문장)
- `H-n`: 숨은 요구사항
- `C-n`: 결정이 필요한 항목

## 절별 지침

### §0 원문 문장 목록

- 원문을 위에서부터 문장 단위로 쪼개 `S-n`을 붙인다
  - 빠뜨리는 문장이 없어야 한다
- 문장은 **그대로** 옮긴다. 고치거나 요약하지 않는다
- 문장마다 한 줄로 끝낸다
  - 태그 하나: `[기능]` · `[비기능]` · `[제출]` · `[배경]`
  - 판정 하나: `→ 명확` · `→ H-n` · `→ C-n` · `→ 기본값` · `→ §2`
- **데이터 표**(기초 데이터 · 요금표 · 코드표 등)
  - 표 전체를 `S-n` 하나로 적고, 표 이름과 행 수를 쓴다
  - 행마다 쪼개지 않는다
  - 판정은 반드시 `→ 03 §9 · data.sql 행 단위 대조`
  - 표 안의 값이 서로 모순되거나 규칙과 어긋나면 §2에서 다룬다

### §1 (삭제)

- 채우지 않는다. 자리표시 한 줄을 그대로 둔다

### §2 위험 문장 심문

- 대상: 아래 기준 중 하나라도 맞는 문장 **전부**. 개수 상한은 없다
  - 해석이 둘 이상으로 갈린다
  - 상태 · 시간 경계 · 동시 요청 · 배치가 걸린다
  - 원문의 검증 요구 · 평가 항목과 연결된다
- 문장마다 세 줄로만 쓴다
  - 모호: 빠진 상태값 · 숫자 · 순서 · 단위 · 경계
  - 깨짐: 실제로 지켜지지 않는 시나리오 (사용자 행동 · 외부 시스템 · 동시 요청 · 시간 · 배포)
  - `→ H-n` / `→ C-n` / `→ 기본값`

**기능 간 교차**

- 상태나 날짜를 바꾸는 기능끼리, 그리고 배치와 요청 사이를 **쌍으로** 훑는다
  - 쌍마다 한 줄: `A × B: 겹칠 때 생기는 일 → H- / C- / 기본값 / 없음`
- 반드시 볼 것
  - 같은 날 두 기능이 연달아 일어날 때 (예: 사용 직후 정지)
  - 한 기능이 다른 기능의 기간 · 수량을 바꿀 때 (예: 해제가 종료일을 줄임)
  - 배치 실행 시각과 요청이 겹칠 때 (예: 자정 직후 요청)
  - 경계값이 여러 날에 걸친 구간일 때 (시작일만이 아니라 끝날도)
- 이전 과제에서 구현 도중 나온 결정은 대부분 여기서 잡을 수 있었다

### §3 숨은 요구사항

- `H-n`을 **항목당 한 줄**로 적는다
  - 형식: `H-n. 요구사항 (← S-n / 깨짐: 한 구절)`
  - 원문에는 없지만 §2의 시나리오를 막으려면 필요한 것
- "관점별 확인"은 체크 목록 한 줄씩 채운다
  - 해당하면 `[x] … → H-n`, 해당 없으면 `[ ] … → –`

### §4 결정이 필요한 항목

- 사용자에게 묻는 `C-n`은 **최대 15건**이다
  - 평가 비중(§5.2)이 큰 쟁점부터 올린다
    - 기준: 틀리게 정하면 핵심 흐름 · 정합성 · 동시성 평가가 깎이는 것
  - 루트 `CLAUDE.md` "상시 결정"으로 풀리는 쟁점은 `C-n`으로 만들지 않는다
  - 나머지 빈틈은 합리적 기본값으로 처리해 "기본값 적용"에 **모두** 한 줄씩 적는다
    - 형식: `[상시]` 또는 `[기본]` 빈틈 → 값 (근거)
    - 빠뜨리는 것이 아니라 묻지 않을 뿐이다. §0 · §2에서 기본값으로 판정한 빈틈은 전부 여기 있어야 한다
- `C-n` 형식
  - 제목: `C-n. 쟁점 한 줄 (S-n · H-n)`
  - 선택지 2~3개, 한 줄씩: `A — 장점 … / 단점 …` (추천안이 1번)
  - `추천: {번호} — {이유 한 줄}`
- "범주별 확인"은 범주당 한 줄, 끝에 `→ C-n` / `→ 상시 결정` / `→ 기본값`
  - 과제에 해당하는 범주만 남긴다

### §5 평가자 관점

- 근거: 원문의 "제출" · "검증 요구" · "평가" 절
  - 없으면 "평가 기준 명시 없음"이라 적고 강조 · 반복 · 난이도에서 추론한다 (`(확인 필요)`)
- 5.1 역량 · 5.2 비중 순서 · 5.3 포기 시 감점 / 대체 가능

### §6 (삭제)

- 채우지 않는다. 도메인 용어는 `03` §1이 쓴다
